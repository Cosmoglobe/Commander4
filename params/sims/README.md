# Feature tests on simulated TODs

Each file here analyses a simulation generated by [`simgen`](../../simgen/README.md). They
come in pairs: the simgen file injects a known truth, the Commander4 file turns on the sampler that
should recover it and *starts it away from that truth*, so a run that does nothing is visibly
distinguishable from a run that works.

| Feature under test | simgen file | Commander4 file | Ranks |
|---|---|---|---|
| Gain calibration + raw detector units | `param_gain.yml` | `simparam_gain.yml` | 12 |
| `corr_noise`: n_corr, PSD parameters, sigma0 | `param_corrnoise.yml` | `simparam_corrnoise.yml` | 6 |
| CG amplitudes, C(l) prior, fluctuations, `scalars` init | `param_compsep.yml` | `simparam_compsep_only.yml` | 18 |
| MH spectral-index sampling | `param_compsep.yml` | `simparam_compsep_MCMC.yml` | 18 |
| Per-pixel solver + `common_res_fwhm` | `param_compsep.yml` | `simparam_compsep_only_perpix.yml` | 18 |
| Partial sky `sparse_maps` + `amp_prior_mean_map` | `param_patch.yml` | `simparam_patch.yml` | 12 |
| Bolometer transfer function (CG deconvolution) | `param_transfunc.yml` | `simparam_transfunc.yml` | 18 |

The simgen files are all in `simgen/params/`; the Commander4 files are all here. Files test
more than one thing where the concepts genuinely reinforce each other: the gain test runs in raw
detector units because a gain of 1e-9 puts the unit bookkeeping under test at the same time, and
the prior mean lives in the partial-sky test because outside the patch the solution is prior-driven
and mu is directly observable there.

### Beams are deliberately wide-spread

Every multi-band simulation now spans a large range of beam widths, so that smoothing, deconvolution
and the mixing matrix are exercised rather than nearly cancelling. Measured as the ratio of the
sharpest to the broadest beam window:

| simulation | beams | l=50 | l=100 | l=150 |
|---|---|---|---|---|
| `param_compsep.yml` / `param_transfunc.yml` | 120'-40' | 1.28x | 2.68x | 9.13x |
| `param_gain.yml` | 120'-40' | 1.28x | 2.68x | 9.13x |
| `param_patch.yml` | 70'-30' | 1.08x | 1.36x | 2.00x |

Before this, `param_compsep.yml` reached only 1.17x at l=100 and `param_patch.yml` had three
identical beams, so a bug in beam handling barely registered. `param_corrnoise.yml` is single-band
and has no spread to give.

### The transfer-function pair

`param_transfunc.yml` applies a single-pole bolometer response (τ = 150 ms) to every band.
`simparam_transfunc.yml` is the only file here that sets `mapmaker: "CG"`. A band's `tau_ms` (or
`tau_sec`) gives the CG mapmaker the transfer function T to deconvolve. Only Band30GHz sets it, so
the other bands are solved with T = 1, which ignores the response. Two limits apply:
- The sky model, orbital dipole and far sidelobes are subtracted without T. With T on, the
  residuals and the n_corr, gain and χ² steps therefore keep (1 − T) times these models.
- The binned mapmaker ignores T.

### Running the transfer-function comparison

`param_transfunc.yml` is a copy of `param_compsep.yml` with only the bolometer response switched on
at the same seed, and `simparam_transfunc.yml` is a copy of `simparam_compsep_only.yml` with only the
paths, the mapmaker and Band30GHz's `tau_ms` changed. The input sky and the noise realization are
therefore identical between the two runs:

```bash
mpirun -n 12 c4-simgen -p simgen/params/param_compsep.yml      # TF off, the reference
mpirun -n 12 c4-simgen -p simgen/params/param_transfunc.yml    # TF on
mpirun -n 18 commander4 -p params/sims/simparam_compsep_only.yml
mpirun -n 18 commander4 -p params/sims/simparam_transfunc.yml
```

The measurements below predate the 2400-scan Planck-like coverage update and the CG deconvolution:
they are the old 400-scan baseline, analysed with the binned mapmaker and no deconvolution, and must
be refreshed after the new pair is analysed. At the current
beams (120'-40'), that old pair gave reduced chi^2 **0.996 -> 2.670** over all bands, and the
recovered CMB amplitude's rms error against truth **9.6 -> 42.4 uK** (truth rms 81 uK, compsep
nside 64, no smoothing).

Per-band, the cost of ignoring the transfer function rises steeply with frequency, because the
sharper beams see more of the scan-direction lag: the residual against the band's own noise rms
goes 1.08 (30 GHz), 1.22 (44), 1.20 (70), 1.40 (100), 3.17 (217), 4.51 (353), against 1.00 in every
band of the TF-off reference.

## Running a pair

```bash
mpirun -n 8 c4-simgen -p simgen/params/param_gain.yml     # writes ../c4_sims/simgen_gain/
mpirun -n 12 commander4 -p params/sims/simparam_gain.yml
```

Each Commander4 file's header states the injected truth, the deliberately-wrong starting value, and
what to look at in the chain files and the log. A run puts all of that under its single
`output.dir`: `logs/`, `chains_bands/`, `chains_compsep/` and `plots/`
(see the [main README](../../README.md#output)). The simulation's `debug_output_dir` holds per-band
diagnostic HDF5 files (input sky, hit map, white-noise RMS, and the injected noise realization
binned with the nominal pointing matrix) to compare the recovered products against.

## Component truth maps

That directory also holds `truth_<Component>.fits`: each component's input **amplitude** — the
unsmoothed sky at its own `nu_ref`, in `uK_RJ` — which is exactly what a Commander4
`DiffuseComponent` carries in its alms. Three uses, all in play here:

- **scoring**: what a recovered component map has to be compared against;
- **`init_from`**: start the chain at the truth, to isolate one sampler from component separation
  converging at the same time. `simparam_corrnoise.yml` does this, which is what lets it sample
  correlated noise from the very first iteration instead of waiting for a sky model;
- **`amp_prior_mean_map`**: the mean μ of the Gaussian amplitude prior, the only way to exercise
  that path with a non-trivial μ. `simparam_compsep_only.yml` carries a commented-out example.

Declare `units: "uK_RJ"` and the matching `nu_ref` on the component reading the file, so the unit
conversion at read time is the identity. See the [simgen README](../../simgen/README.md) for
the exact convention.

## What these pairs deliberately do not cover

The simulator cannot yet inject the following, so the corresponding samplers have nothing to
recover and are switched off in every file here except where noted:

- **Per-scan gain drift.** `simgen` gives each detector one constant `gain`, so
  `tod_processing.temporal_gain` has no signal. Needs a per-(scan, detector) gain model in simgen;
  it is switched off everywhere here.
- **Flags, gaps and jumps.** `simgen.writers.write_scan_file` writes an all-zero flag stream, so
  `sample_jump_detection`, `gap_fill_method`, `data_selection.min_good_fraction` and the CG
  mapmaker's zero weighting of flagged samples are all inert.
  The reader side is ready for them: the `general` reader passes the flag stream through to
  `DetectorTOD` per sample, so injecting flags in simgen is now the only missing half.
- **Bad detector-scans.** Nothing injects glitches or corrupted scans, so
  `data_selection.chisq_abs_threshold` never fires. `simparam_corrnoise.yml` and
  `simparam_patch.yml` still enable data selection, but only as a diagnostic: the reported
  `chisq_z` quantiles measure how well the sampled noise model whitens the residual.
- **Spatially varying spectral indices.** `simgen` scales one template by a scalar SED, so
  `spatially_varying_MM` and per-pixel index sampling see a constant-index sky. (This is also why
  the truth maps are a single map per component rather than a map per parameter.)
- **Bolometer transfer functions end to end.** The CG mapmaker deconvolves one single-pole T per
  band, but the model TODs are subtracted without T (see the transfer-function pair above).

# simparam_compsep_only.yml
Commander4: CG amplitude-sampling feature test.

Analyses `simgen/params/param_compsep.yml`, which describes the simulation and the truth it
injects. Generate the TODs first, then run this:
    mpirun -n 12 c4-simgen -p simgen/params/param_compsep.yml
    cd ..   && mpirun -n 18 commander4 -p params/sims/simparam_compsep_only.yml
18 tasks = 6 TOD + 6 CompSep-I + 6 CompSep-QU.

FEATURES UNDER TEST:
  * `compsep.cg_sampling_groups`, the constrained realization of the component amplitudes solved
    in `compsep/cg_solver.py`,
      (1 + S^1/2 A^T N^-1 A S^1/2) x = S^1/2 A^T (N^-1 d + N^-1/2 eta_1) + S^-1/2 mu + eta_2,
    with a = S^1/2 x. The TOD side is deliberately inert: nothing is sampled there.
  * Initialisation from each scan's `scalars` dataset. The `detectors:` entries below name the
    detectors but carry no `gain`, and no band states `initial_noise_params`, so both come from
    the files simgen wrote. Every other file here overrides them to start away from the truth,
    which is right for a TOD test but means this is the only place that read path runs.

WHAT TO CHECK:
  * The component maps in `<output_dir>/chains_compsep/` against the simulation's `truth_*.fits`.
  * The per-band chi^2 logged each iteration: with an exact model it should sit at the number of
    degrees of freedom.
  * `optimize` is the switch between a genuine Gibbs draw and the Wiener/MAP mean. Run it both
    ways and compare the scatter of the CMB power spectrum across iterations: with
    `optimize: false` the recovered C(l) should be unbiased, with `optimize: true` biased low
    where the noise starts to dominate. That is the direct test of the fluctuation terms.



# simparam_compsep_only_perpix.yml
Commander4: per-pixel amplitude solver + common-resolution smoothing feature test.

Analyses `simgen/params/param_compsep.yml`, the same six-band simulation as the CG amplitude test.
Generate the TODs once, then either analysis can read them:
    mpirun -n 12 c4-simgen -p simgen/params/param_compsep.yml
    cd ..   && mpirun -n 18 commander4 -p params/sims/simparam_compsep_only_perpix.yml
18 tasks = 6 TOD + 6 CompSep-I + 6 CompSep-QU.

FEATURES UNDER TEST, neither of which any other file here reaches:
  * `compsep.per_pixel_sampling_groups`, the per-pixel least-squares amplitude solver in
    `compsep/perpix_solver.py`. It is the alternative to the global CG solve and is mutually
    exclusive with it, so `cg_sampling_groups` is empty below.
  * `compsep.common_res_fwhm`, the noise-weighted smoothing of every band to one beam, applied at
    the data sources on read (`data_models/detector_map.py`). The per-pixel solver has no beam
    model at all, so without this it would silently mix resolutions.

The two go together: the per-pixel solver is only correct once all bands share a beam. The shared
simulation's beams span 120' to 40', so `common_res_fwhm` is set to the broadest of them. No
separate simulation is needed; smoothing belongs to the analysis, not the data generation.

Unlike the CG solver, the per-pixel solver returns amplitudes *at* the common resolution rather
than deconvolved, so the recovered maps must be compared against the simulation's truth maps
smoothed to 120', not against the truth maps directly. The chain records which of the two a file
holds: `comps/<name>/amp_fwhm_arcmin` is 120 here and 0 for a deconvolved CG solve.

WHAT TO CHECK:
  * The component maps in `<output_dir>/chains_compsep/` against `truth_<Component>.fits` from the
    simulation, smoothed to 120'.
  * `maps/observed_sky` - `maps/skymodel` in `<output_dir>/chains_bands/`, against `maps/rms`.
    Both maps are at the beam named by `metadata/map_fwhm_arcmin` (120' here, since
    `common_res_fwhm` is set), so the residual is meaningful as it stands.
  * Run the same simulation through `simparam_compsep_only.yml`'s solver settings and compare. At
    common resolution the per-pixel and CG solutions should agree where the data constrain them;
    a disagreement that tracks the beam spread is a smoothing bug.
  * The startup warning from `solve_compsep_perpix` if the bands reach it at different
    resolutions. It must not fire here, and firing means `common_res_fwhm` was ignored.

KNOWN, NOT A BUG: common-resolution smoothing correlates the noise between neighbouring pixels,
while only a per-pixel rms is carried through it, so the reduced chi^2 is not expected to be
properly normalized. Fixing that needs a noise model that survives smoothing, not a separate
simulation or a change to this parameter file.



# simparam_compsep_MCMC.yml
Commander4: spectral-index (MCMC) sampling feature test.

Analyses `simgen/params/param_compsep.yml`, the same simulation as `simparam_compsep_only.yml`,
which describes it and the truth it injects. Generate the TODs first, then run this:
    mpirun -n 12 c4-simgen -p simgen/params/param_compsep.yml
    cd ..   && mpirun -n 18 commander4 -p params/sims/simparam_compsep_MCMC.yml
18 tasks = 6 TOD + 6 CompSep-I + 6 CompSep-QU.

FEATURE UNDER TEST: `compsep.mcmc_sampling_groups` with `parameters: spectral_indices`, the
Metropolis-Hastings sampler in `compsep/spectral_index.py`, which re-solves the CG amplitude
groups named in `update_amplitude_groups` between proposal and accept/reject.

STARTS AWAY FROM THE TRUTH AT: beta_dust 1.45 (truth 1.54), beta_sync -3.25 (truth -3.10), several
proposal widths out, so a working sampler has to walk back and then scatter around the truth.

WHAT TO CHECK: the sampled spectral indices in `<output_dir>/chains_compsep/`, and the MH
acceptance rate logged each iteration. Walking to the truth and then mixing at roughly 0.2-0.5
acceptance is the pass condition; a chain that sticks means `spectral_index_proposal_sigma` is too
large, one that random-walks without converging means it is too small.

NOTE that the amplitude fluctuations (the CG group's `optimize: false`) make the MH likelihood
stochastic, since each proposal is evaluated against a freshly drawn amplitude realization. This
matches Commander3 but is a known approximation; set `optimize: true` to make the likelihood
deterministic and isolate the index sampler.



# simparam_transfunc.yml
Commander4: bolometer transfer-function impact test.

Analyses `simgen/params/param_transfunc.yml`, which describes the simulation and why the
pair is a controlled difference rather than a recovery. Generate the TODs first, then run this:
    mpirun -n 12 c4-simgen -p simgen/params/param_transfunc.yml
    cd ..   && mpirun -n 18 commander4 -p params/sims/simparam_transfunc.yml
18 tasks = 6 TOD + 6 CompSep-I + 6 CompSep-QU.

This file is a copy of `simparam_compsep_only.yml` with only the paths (the six TOD filelists, the
output directory and the log file), the mapmaker (`"CG"`) and Band30GHz's `tau_ms: 150.0` changed.
So only Band30GHz deconvolves the bolometer response; the other bands are solved as if T = 1. The
model TODs (sky model, orbital dipole, far sidelobes) are subtracted without T.

WHAT TO CHECK, always against the TF-off reference run and never against an absolute.

The numbers below were measured at the current beams (120'-40'), 20 iterations, compsep nside 64,
with the binned mapmaker and no deconvolution, so they show what ignoring the response costs. They
are reference points, not pass thresholds: the transfer function's imprint depends on the beam, so
re-measure both halves if the beams change again.
  * `<output_dir>/chains_bands/SimSat_<band>_chain01_iter0001.h5`, `maps/observed_sky`. The TOD
    side is inert, so this map is a deterministic function of the TODs and differencing it against
    the reference is the cleanest available measurement. Expect a scan-direction lag, largest
    where the sky gradient across the scan is largest. Measured: rms(difference) is 15-24% of the
    map rms, rising with frequency from 13.8 uK_RJ at 30 GHz to 178 uK_RJ at 353 GHz.
  * The per-band chi^2 logged each iteration. Measured at iteration 20: reduced chi^2 over all
    bands 0.996 (reference) against 2.670 (here). Per band the residual against the band's own
    noise rms goes 1.08, 1.22, 1.20, 1.40, 3.17, 4.51 from 30 to 353 GHz, against 1.00 throughout
    in the reference: the sharper the beam, the more scan-direction lag survives.
  * The component maps against the simulation's `truth_*.fits`. A transfer function is not one of
    the fitted components, so the solve has nowhere to put the residual and spreads it over all
    three; the CMB pays most. Measured rms error against truth in intensity: CMB 9.6 -> 42.4 uK
    (4.4x), dust 105 -> 245 uK_RJ (2.3x), synchrotron 68 -> 80 uK_RJ (1.2x).



# simparam_corrnoise.yml
Commander4: correlated-noise / noise-PSD feature test.

Analyses `simgen/params/param_corrnoise.yml`, which describes the simulation and the truth it
injects. Generate the TODs first, then run this:
    mpirun -n 8 c4-simgen -p simgen/params/param_corrnoise.yml
    cd ..   && mpirun -n 6 commander4 -p params/sims/simparam_corrnoise.yml
6 tasks = 4 TOD + 1 CompSep-I + 1 CompSep-QU.

FEATURE UNDER TEST: `tod_processing.corr_noise`, i.e. the n_corr constrained realization, the
noise-PSD parameter sampler and the white-noise estimator, in `tod/noise/sample_ncorr.py`.

STARTS AWAY FROM THE TRUTH AT: `initial_noise_params: [80.0, 0.1, -1.0]` against a truth of
[80.0, 0.5, -1.5], so the knee is 5x too low and the slope too shallow.

WHAT TO CHECK: the `noise_params` dataset in `<output_dir>/chains_bands/` (columns
[sigma0, fknee, alpha], per detector-scan) and the per-iteration correlated-noise summary logged
by `log_corr_noise_stats`. The correlated-noise maps are written to the chain, so the recovered
n_corr can be compared against `maps/noise` in the simulation's diagnostic HDF5.

The CMB is initialised from the simulation's truth map, so even the first iteration's residual is
pure noise and the sky model cannot feed the noise sampler power to mistake for 1/f.
